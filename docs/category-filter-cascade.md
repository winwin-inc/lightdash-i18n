# 类目筛选器联动

## 职责划分

| 能力                                                     | 数据源                                                                                              |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 看板可见性（客户使用模式 + viewer / interactive_viewer） | Admin RPC `findAllDashboardByMobile`（未配置 `ADMIN_API_HOST` / `ADMIN_API_KEY` 时不调，只走 CASL） |
| 类目默认值 / 父子联动 / 下拉选项                         | `field/search`（含 `dashboardSlug` → dbt `sql_filter` / `dim_ld_employee_categories`）              |

类目联动**不再**调用 Admin 类目树（已移除 `GET /dashboard-categories`）。

## 前置条件

- 非编辑模式，且已有 `projectUuid` 与 `dashboardSlug`（slug 未就绪时不初始化 / 不联动，避免按 `NA` 绕过控制码）
- 联动 `field/search` 会带上目标筛选项**左侧**已有值的条件（如时间）以及父级类目，与下拉级联对齐

## 核心思路

首次加载和父改子联动使用同一套逻辑：

1. 用 `field/search` 取仓库实际可选类目（左侧筛选 + 父级 + `dashboardSlug`）
2. 当前值在结果中 → 保留
3. 否则 → 取结果第一个（第一个有权限且底层表真实存在的类目）
4. 请求成功但结果为空 → **无法区分**「底层表确实没有该类目」与「行级过滤（`sql_filter`）把候选值全部过滤掉」→ **保留原值**（既不清空也不禁用）
   - 例外：被旧逻辑误清空、但**服务端仍保存着原值**的筛选器 → 额外用一次**不带级联**的查询恢复
5. 请求失败 → 无法判断，保留原值（不改变用户筛选语义）

> 空结果**不会**额外发起「不带级联」的兜底查询：保留原值与「兜底命中当前值」的结果完全一致，
> 多出来的请求只会让初始化变慢。请求量与本文档改造前保持一致。

> **为什么空结果不再清空筛选器** > `field/search` 的空结果有两种成因，接口层面无法区分：类目在表里真的不存在，或行级控制码把候选值全过滤掉了。
> 误清空会直接抹掉看板里已经保存的类目，且由于筛选器同时被置为 `disabled`，
> 后续的初始化与联动都会跳过它，**该筛选器再也回不来**（表现为「底层表有值，但筛选器里选中的值为空」）。
> 因此空结果一律保留原值，候选值缺失只会让下拉列表少几个选项，不会丢用户的选择。

类目权限与存在性**统一以底层表实际查询结果为准**，不再依赖 Admin 用户类目接口（admin 用户同样走这套逻辑）。

## 用户选择不被自动逻辑覆盖

- 初始化（`initializeCategoryFiltersAsync`）与联动（`updateCategoryFilterCascadeAsync`）使用**独立的 generation**：
  自动初始化不会作废用户刚刚的选择，用户的选择也不会被自动初始化重置
- 用户手动改动类目时：立即把选择写入筛选状态（与普通筛选一致，会置 `haveFiltersChanged` 并记录 saved filter override，
  否则选择无法保存、刷新后会变回空值），随后的联动只修正**子孙级**
- 联动之后的初始化会跳过用户刚刚改的那一级（`skipFilterIds`），显式选择优先于自动解析
- 用户的显式选择被标记为「已处理」：同一组筛选条件不会重复自动解析；
  等其他条件变化导致签名改变时，仍会重新校正（类目已不在权限范围内时重置为第一个有权限的类目）
- 临时筛选器（图表交叉筛选，`isTemporary`）**不做**类目联动：联动结果会写回永久筛选器，污染看板自身的类目配置

## 三种场景

### 场景 1: 首次加载（看板初始化，非编辑模式）

- 配置了默认值的类目筛选器（`disabled === false`）
- 当前值在 `field/search` 结果中 → 保留
- 否则 → 切换到第一个实际值
- 处理顺序按**类目层级（一级 → 四级）**，父级先重置，子级再基于新的父级值重新解析（级联）
- 父级无候选值时，子级保留当前值（不连带清空）
- **被禁用的筛选器不参与自动赋值**（既有语义：`disabled` = 没有配置默认值，保持为空/无限制，不能给它套默认值）
- 只有「被旧逻辑误清空、且服务端仍保存着原值」的类目筛选器才会恢复：重新解析出值并重新启用（`disabled: false`）
  - 判据：`originalDashboardFilters`（服务端保存值）里该筛选器仍有值，而当前状态里是 `disabled` 且无值
  - 由此区分「作者本来就没配默认值」与「旧逻辑误清空」，避免给未配置的筛选器乱套默认值

### 场景 2: 用户切换父级筛选器

- 子级按父条件 + 左侧筛选再查 `field/search`
- **参与联动的判据是「当前是否有确认选中的值」**（而不是 `disabled` 标记本身）：
  - 有确认选中的值 → 参与。父级变了，下级必须跟着变；
    `disabled` 只说明「作者没配默认值」，若当前确实有选中的值（历史配置残留或用户在看板里选过），
    不能因此丢掉联动（否则表现为「上级变了、下级没变」）
  - 没有值 → 沿用初始化语义：`disabled`（作者没配默认值）不参与、不发请求；
    未禁用（未设置默认值的控件）参与并按实际数据补齐
- 父级条件取父级「当前确认选中的值」：即使父级还带 `disabled` 标记也要带上，
  否则子级会退化成「不带父级条件」的查询，联动结果与类目层级对不上
- 当前值有效 → 保留，并继续向下级联
- 当前值无效 → 切换到第一个，再向下级联
- 被联动的子级若原本带 `disabled` 标记，会随更新恢复为可用状态（值是实际选中的，筛选器应当生效）

### 场景 3: 用户手动修改子级

- `operator !== EQUALS`（如 NOT_NULL）→ 不被联动覆盖

## 可信 dashboard context

`field/search` 携带的 `dashboardSlug` 会参与 dbt `sql_filter`（行级控制码）。因此后端会先用数据库校验该 slug：

- 看板必须属于目标项目
- 当前用户必须有该看板所在空间的查看权限（CASL）
- 客户使用模式下看板必须在白名单内

校验失败时**不会回退使用客户端传来的 context**（避免伪造 slug 绕过行级过滤），此时按普通 ad-hoc 查询口径校验 explore 白名单。

## 联动请求的条件（`field/search` payload）

联动的 `field/search` 条件**必须与下拉搜索发送的规则一致**（对齐 `getAutocompleteFilterGroup`），
后端按规则原文编译 SQL，因此：

- **不能丢 `settings`**：日期条件的单位（`unitOfTime`）与 `completed` 都在 `settings` 里。
  丢掉后后端按默认的「天」编译，「过去 13 个月」会退化成「过去 13 天」，
  条件被收窄到查不到数据（表现为联动没有候选值、下级不更新）
- **不能带 `disabled`**：编译器遇到 `disabled` 会直接渲染 `1=1`，
  等于把这个条件整个丢掉（父级带 `disabled` 时尤其容易踩到）
- `tileTargets` 只用于图表定向，查询时不需要，不发送

> 对照：本仓库的 `renderFilterRuleSql` 中
> `const unitOfTime = filter.settings?.unitOfTime || UnitOfTime.days;`
> —— 没有 `settings` 就是「天」。

## 加载时序（类目解析与图表查询）

- 首屏加载时，类目筛选器要先按 `field/search` 解析出实际类目（`initializeCategoryFiltersAsync`），
  解析完成前**图表不发起查询**（`isCategoryResolutionPending`），
  解析完成后按最终类目一次性查询，避免图表先按「未解析的类目」跑一次、解析完再刷新一次
- 该等待只作用于首屏解析：后续用户改筛选条件不再等待类目解析（改完立即查询，类目解析完成后再校正一次）
- 没有类目筛选器 / 编辑模式 / slug 未就绪 → 不等待
- 等待有上限（10s）：超时后先放行图表，类目解析完成后再校正一次，避免 `field/search` 卡住时看板一直转圈

## 验证

1. 首次加载：默认值在实际数据中 → 保留
2. 首次加载：默认值不在实际数据中 → 切到第一个
3. 首次加载：`field/search` 返回空 → 保留原值（不清空、不禁用），且不发起额外请求
4. 首次加载：请求失败 → 保留原值
   4.1 首次加载：筛选器处于「已清空 + 禁用」状态、且服务端仍保存着原值 → 恢复出值并重新启用
   4.2 首次加载：筛选器被禁用、且服务端也没有值（作者本来就没配默认值）→ 保持为空，不发请求、不套默认值
5. 父改子：子级无效 → 切到第一个；有效 → 保留
6. 联动请求 SQL 含 `short_name = dashboardSlug`（非 `NA`）
7. 已选时间等左侧条件时改一级：二级落在该时间 + 父级下有数的值
8. 用户改为非 EQUALS → 不被覆盖
9. 编辑模式 → 不自动改筛选值
10. 客户端伪造 `dashboardSlug` → 后端校验失败，不使用该 context
11. 用户选中一级类目 → 立即显示并可保存；二级类目不会被自动清空
12. 自动初始化与用户选择并发 → 用户的选择不被丢弃
13. 图表交叉筛选产生的临时类目筛选器 → 不改动看板自身的永久类目筛选器
14. 初始化与联动的请求次数不因本次改造增加
15. 被禁用的类目筛选器（没有配置默认值）→ 不被自动赋值、不参与联动、不发请求
16. 被禁用但**当前有确认选中的值**的类目筛选器 → 父级变化时跟着联动，并恢复为可用状态
17. 首屏加载：类目解析完成前图表不发起查询，解析完成后按最终类目一次性查询（不出现「先出一版未解析的数据再刷新」）
18. 联动请求的条件保留 `settings`（日期单位 / `completed`），且不以 `disabled` 状态发送
    （否则日期条件退化为「天」、父级条件被编译成 `1=1`）

# 查询性能优化方案

状态：草案，未实施。
范围：图表与看板的查询链路。导出链路的改动见 [`csv-export-performance.md`](./csv-export-performance.md)，两边的耗时如何区分见本文第 6 节。

## 1. 背景

导出侧优化完成后，客户感知的耗时里还剩很大一块是"查询本身"。本文只讨论这一块：从点击图表到拿到结果，中间发生了什么、哪些是应用层能改的、哪些必须动建模或数仓。

先明确一个前提：查询耗时由三部分组成——数仓执行 SQL、把结果行回传给服务进程、把结果写成可复用的结果文件。第一部分占比通常最大，但只有后两部分是应用层能动的。

## 2. 现状

### 2.1 查询怎么走

1. 前端发起异步查询，后端创建一条 `query_history` 记录，状态 pending。
2. 查询在**服务进程的主循环里执行**（`runAsyncWarehouseQuery` 是 fire-and-forget），没有独立的查询进程。
3. 结果边取边写：每行序列化成 JSONL，通过上传流写进对象存储；写完才把状态改成 ready。
4. 页面分页读结果时，从对象存储把 JSONL 读回来，`getResultsPageFromS3` 每次**从文件第 0 行开始扫**，扫到目标页为止。
5. 导出另起一个后台任务，把同一份 JSONL 再读一遍转 CSV/XLSX。

### 2.2 从现有数据能看到的

你们贴的 `query_history` 里，最近一段时间的查询是这样的：

- 类型全是 `exploreView` / `dashboardView` / `mcp`，返回 1–500 行
- 数仓耗时 99–1077 ms，没有一条超过 1.5 秒
- 同一秒（`03:46:24`）里有 20 多条 `dashboardView` 查询，各 0.5–1.1 秒

这组数据说明两件事：单条查询本身不慢；看板打开时的**并发**是另一回事。

表本身的规模：23.5 万行占 2.4 GB，每行约 10 KB（存了 `compiled_sql`、`metric_query`、`fields`）。按时间检索没问题，按内容全文检索会拖慢数据库。

### 2.3 结构性缺口

- **没有查询结果缓存**。v2 的结果缓存（`query_history` + JSONL 复用）依赖企业版授权，当前实例没有 license，`cacheService` 不会注册，同样的图重复打开每次都是真查。老版本的 S3 结果缓存只服务 v1 路径，对现在的图表无效。
- **导出会重跑一次查询**。选「所有结果」时前端用 `LIMIT 2147483647` 重新执行一次，页面已查过的结果不复用；因为 `LIMIT` 进了 SQL，缓存键跟着变，必然不命中。
- **翻页是线性重扫**。第 N 页要把前 N 页的字节全部下载并逐行计一遍，页数越大越慢。
- **看板不做区分**。首屏把所有 tile 的查询一起发出去，不管是否在可视区域、不管 Tab 是否激活。

## 3. 第一层：应用层可以做的

不改 SQL 语义，只改"什么时候查、查几次、怎么读结果"。

### 3.1 看板首屏按可见性发起查询

现状是整页所有 tile 同时查。做法是按可视区域和激活 Tab 分批（首屏一批、滚动到再一批），或对同一张表、同一组筛选条件的 tile 做合并。

预期：看板打开时的并发查询数从"全部"降到"可见的几个"，数仓瞬时压力随之下降，首屏出图更快。

成本：前端改动为主，需要处理懒加载后的占位与布局跳动。风险中等，涉及看板渲染逻辑。

### 3.2 导出复用页面上的查询结果

「表格结果」已经复用页面 query；「所有结果」会重跑。两种改法：一是导出时不再重跑，直接按页面结果文件导出（受页面 limit 限制，需要产品确认可接受）；二是保留重跑，但把查询上限对齐导出口径，避免拉回全表又截断。

预期：省掉一次全表扫描与一次全量落盘。对 70 万行的表，省的是几十秒到几分钟不等，取决于数仓。

成本：前后端各改一处，加行数断言。风险在于口径变化，需要产品确认。

### 3.3 结果分页加行索引

落地结果文件时顺带写一份行偏移索引（每 N 行记一次字节位置），翻页时用 Range 请求定位，不再从头扫。存量文件没有索引，走原来的全量扫，新旧两条路径并存。

预期：翻页从 O(页数 × 每页行数) 降到 O(每页行数)。对大结果集看板的"翻到后面越来越慢"有明显改善。

成本：后端改动，需要处理索引与文件不一致的兜底。风险中等。

### 3.4 结果缓存的现实约束

如果后续引入企业版授权，结果缓存可以直接复用 `query_history` 里已有的 JSONL，重复查询不再打数仓。在拿到授权之前，不建议打开 `RESULTS_CACHE_ENABLED`：它当前只激活老 v1 缓存，写入是整份 `JSON.stringify`，配合 100 万行上限容易把内存打满，而且对 v2 查询无效。

## 4. 第二层：建模与用法

这一层改变的是"发出去的 SQL 长什么样"，不需要改代码，但需要和建模的人一起过一遍。

- **避免 distinct 聚合**。`sum(distinct ...)`、`count(distinct ...)` 在 Hologres 上代价很高，「SPU市占-全量模型」里有这类表达式。能换成预聚合字段就换。
- **时间过滤落在分区列上**。`WHERE date_trunc('month', col) >= ...` 这种写法会让分区裁剪失效，尽量改成对分区列直接比较，把 `date_trunc` 放到 SELECT。
- **少选用不到的维度**。图表里挂了 17 列但只看 8 列时，扫描和回传都白做。列越多，回传时间越长。
- **控制 join 数量**。explore 里挂的 join 越多，单条查询越慢；能落到同一张宽表里的维度尽量提前合并。
- **表计算尽量用 SQL**。有些表计算在应用层完成，需要把更多原始行拉回来再算，能下推到 SQL 的下推。

## 5. 第三层：Hologres 与 dbt

这一层收益最大，也最依赖数据团队。

**Hologres 侧检查清单**（拿 `query_history.compiled_sql` 直接跑 `EXPLAIN ANALYZE`）：

- 是否命中分区裁剪，扫描的数据量与实际需要的是否一致
- 是否发生 shard 间数据重分布（`Redistribute Motion`），能不能靠调整 distribution key 消掉
- clustering key 是否与常用过滤/排序一致
- shard 数是否与数据量和并发匹配
- 统计信息是否过期（过期会导致行数估算错误，进而选错 join 策略）

**dbt 侧可做的**：

- 把「月 × 品类 × 品牌 × SPU」这类固定粒度做成物化宽表或预聚合表。客户导出的是月粒度分析结果，这类聚合最适合预计算。
- 减少视图层数，避免多层嵌套视图导致优化器拿不到有效统计信息。
- 大表加分区，并保证过滤条件能命中分区。

预聚合的代价是数据新鲜度和存储，需要和数据团队确认更新频率。

## 6. 先量后做

不要凭感觉选层。先对出问题的那张图量三个数：

1. `query_history.warehouse_execution_time_ms`：数仓执行耗时。
2. `results_updated_at - created_at`：从发起查询到结果文件写完，含数仓执行与落盘。
3. 导出任务从投递到完成的间隔（`scheduler_log` 里同一 `job_id` 的 started / completed 两行），减去第 2 项，就是导出转换的耗时。

或者更省事：浏览器开发者工具里看 `GET /api/v2/projects/<p>/query/<uuid>` 响应中的 `initialQueryExecutionMs`，以及任务轮询从 `schedule-download` 到 `COMPLETED` 的时间差。

判定：

| 数仓耗时占比 | 结论 |
|---|---|
| 70% 以上 | 走第三层，应用层优化收益有限 |
| 30%–70% | 第三层为主，第一层能省一点是一点 |
| 30% 以下 | 第一层优先，第二层顺手整理 |

另外留意看板的并发情况：如果单条查询都是亚秒级，但看板打开要十几秒，那问题在 3.1 而不是单条 SQL。

## 7. 不建议做的

- 为了让导出零查询，把首屏查询的上限拉到导出上限。等于每次打开看板都全表扫描，成本前置且放大。
- 单纯调大调度并发、任务超时或加 CPU 核数。这些只在"任务排队"时有用，对查询耗时没有任何作用。
- 在没有企业版授权的情况下打开 `RESULTS_CACHE_ENABLED`。当前它只激活老 v1 缓存，写入是整份内存序列化，有 OOM 风险，且对 v2 查询无效。
- 在应用层做"结果伪造缓存"（比如把结果文件按用户缓存起来自己管）。会和权限、行级过滤冲突，风险大于收益。

## 8. 排期参考

| 事项 | 归属 | 预估 | 前置 |
|---|---|---|---|
| 看板首屏按可见性发起查询 | 前端 | 3–5 人日 | 无 |
| 导出复用页面结果 / 对齐上限 | 前后端 | 1–2 人日 | 产品确认口径 |
| 结果分页加行索引 | 后端 | 2–3 人日 | 无 |
| 建模整理（distinct 聚合、分区过滤、列裁剪） | 建模 + 数据 | 按模型数量 | 需要逐张过 |
| Hologres 执行计划调优 | 数据 | 按问题数量 | 先有 `EXPLAIN ANALYZE` 结果 |
| dbt 预聚合 / 物化宽表 | 数据 | 按模型数量 | 确认数据新鲜度要求 |

前两项属于"打开就更快"，第三项属于"翻页更快"，后三项决定单条 SQL 的下限。

# 分支模型（强制）

> 背景：曾发生「把功能分支当成要合回 `release`/`fix/bugs` 才能上线」的误判。本文件写清流向，主控与子 agent 在建议合并/上线动作前必须按此核对。

## 分支职责

| 分支 | 职责 | 谁能往里提交/合并 |
|---|---|---|
| `fix/bugs` | **只承接 bug 修复**，是日常修 bug 的默认开发分支 | bug 修复提交于此；可把 `dev` 合入以获取所需代码 |
| `feat/xx` | 功能开发分支 | 功能提交于此；可定期把最新 `release`/`dev` 合入自己保持基线不过期 |
| `dev` | 功能集成分支 | **由 `feat/xx` 分支合并进入** |
| `pre` / `main` | 预发 / 主干 | 由功能分支（或经 `dev`）按发布安排合并进入 |
| `release` | 发布分支 | **功能分支不要直接合入** |

## 判定规则

1. 手头的改动是 **bug 修复** → 在 `fix/bugs` 上做（详见 CLAUDE.md 开发流程第 0 条）。
2. 手头的改动是 **新功能/重构** → 建 `feat/xx` 分支做，完成后合入 `dev`（或按发布安排 `pre`/`main`）。
3. **禁止**：
   - 把功能分支合入 `release` 或 `fix/bugs`（会污染 bug 修复通道）；
   - 未经确认擅自切到 `dev` 直接提交。
4. 功能分支上线前唯一动作：由 `feat/xx` → `dev`（→ `pre`/`main`），与 `release`/`fix/bugs` 无关。
5. 拿不准某分支的用途或流向时，**先问用户**，不要按其他仓库的惯例推断。

## 给主控的提示

- 评估「要上线还差什么」时：功能分支看的是「是否已合入 `dev`/`pre`/`main`」，不是 `release`。
- 派发子 agent 涉及切分支/合并建议时，把本文件的判定规则写入任务描述。
